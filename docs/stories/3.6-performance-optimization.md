## ✅ ACCEPTANCE CRITERIA

### Given-When-Then Format

**Given** performance testing is configured
**When** load tests are executed
**Then** application should:
- Handle 100 concurrent users with p95 latency < 100ms
- Handle 500 concurrent users with p95 latency < 500ms
- Maintain error rate < 1% under normal load
- Maintain error rate < 5% under peak load
- Recover gracefully after load test completion

**Given** database is optimized
**When** queries are executed
**Then** performance should be:
- p50 query latency: < 50ms
- p95 query latency: < 100ms
- p99 query latency: < 500ms
- No N+1 query problems
- No missing indexes on frequently queried columns

**Given** caching is configured
**When** frequently accessed data is requested
**Then** cache should:
- Reduce database load by 30%+
- Reduce response time by 50%+
- Maintain data freshness (< 5-minute stale)
- Have > 80% hit rate for hot data
- Gracefully degrade if cache unavailable

## 📋 TASKS

### Task 3.6.1: Database Query Optimization
- [ ] Analyze slow query logs:
  - [ ] Enable slow query log (log queries > 100ms)
  - [ ] Review slow queries from past week
  - [ ] Identify N+1 query patterns
  - [ ] Identify missing indexes
  - [ ] Identify inefficient JOINs
- [ ] Add missing indexes:
  - [ ] Identify hot queries (by frequency and impact)
  - [ ] Create indexes on:
    - [ ] Foreign keys (if not already indexed)
    - [ ] Frequently filtered columns (WHERE clauses)
    - [ ] Frequently sorted columns (ORDER BY)
    - [ ] Frequently joined columns (JOIN conditions)
  - [ ] Example queries to optimize:
    - [ ] SELECT * FROM purchases WHERE user_id = ? AND status = 'APPROVED'
    - [ ] SELECT * FROM users WHERE email = ?
    - [ ] SELECT COUNT(*) FROM purchases WHERE created_at > ?
- [ ] Optimize query patterns:
  - [ ] Batch queries: Instead of 100 single queries, 1 batch query
  - [ ] Select only needed columns: SELECT id, email instead of SELECT *
  - [ ] Use EXPLAIN ANALYZE to verify index usage
  - [ ] Consider query caching for read-heavy operations
- [ ] Test optimization:
  - [ ] Run slow query log again
  - [ ] Verify queries improved (< 100ms now)
  - [ ] Monitor query count (should decrease)
  - [ ] Check index size (shouldn't bloat database)

### Task 3.6.2: Connection Pool Optimization
- [ ] Review PgBouncer configuration:
  - [ ] Current settings: pool_size, min_pool_size, max_pool_size
  - [ ] Monitor connection usage: Peak vs baseline
  - [ ] Monitor connection wait time (should be < 10ms)
- [ ] Optimize settings based on load:
  - [ ] Adjust pool_size based on peak load observed
  - [ ] Set reserve_pool_size for burst traffic (10-20% of pool)
  - [ ] Adjust timeout values for application patterns
  - [ ] Enable connection idling (close idle connections after 5 min)
- [ ] Monitor and tune:
  - [ ] Measure pool utilization percentage
  - [ ] Monitor queue wait time
  - [ ] Alert if utilization > 80%
  - [ ] Document optimal settings

### Task 3.6.3: Application Caching Strategy
- [ ] Implement in-memory cache (Redis recommended):
  - [ ] Set up Redis instance (single node for now, cluster later if needed)
  - [ ] Configure TTL: 5 minutes for user/product data
  - [ ] Configure TTL: 1 hour for analytics data
  - [ ] Use cache-aside pattern: Try cache, fall back to DB
- [ ] Cache hot data:
  - [ ] User profiles (by email, by ID)
  - [ ] Product catalog (all products, by category)
  - [ ] Recent purchases (for dashboard)
  - [ ] Analytics summaries (daily/hourly)
- [ ] Implement cache invalidation:
  - [ ] On user profile update: Invalidate user cache
  - [ ] On product update: Invalidate product cache
  - [ ] On purchase: Invalidate user purchase cache
  - [ ] Time-based: Automatic expiration (TTL)
- [ ] Monitor cache effectiveness:
  - [ ] Cache hit rate (target: > 80%)
  - [ ] Cache miss rate
  - [ ] Cache eviction rate
  - [ ] Database load (should decrease by 30%+)
- [ ] Handle cache failures:
  - [ ] If Redis down: Fall back to database
  - [ ] If cache error: Log and continue (don't block user)
  - [ ] Graceful degradation: Slower but functional

### Task 3.6.4: API Response Optimization
- [ ] Implement response compression:
  - [ ] Enable gzip compression on API responses
  - [ ] Measure compression ratio (typically 60-70% reduction)
  - [ ] Verify client support (most browsers/clients support)
- [ ] Optimize JSON payloads:
  - [ ] Remove unnecessary fields from responses
  - [ ] Use field selection API (allow client to specify fields)
  - [ ] Paginate large result sets (default: 50 items, max: 500)
  - [ ] Use sparse fieldsets for related data (embed only needed fields)
- [ ] Implement pagination:
  - [ ] Cursor-based pagination (more efficient than offset)
  - [ ] Endpoint: GET /api/purchases?cursor=xyz&limit=50
  - [ ] Include next_cursor in response for pagination
  - [ ] Performance: < 100ms per page
- [ ] Optimize webhook payloads:
  - [ ] Send only changed fields (not entire object)
  - [ ] Batch multiple webhooks if possible
  - [ ] Include retry logic with exponential backoff
  - [ ] Test webhook latency (target: < 1 second)

## 📌 DEV NOTES

- Start with baseline testing before optimization (measure first)
- Not all optimizations have equal impact; measure and prioritize
- Consider trade-offs: More caching = more complexity and stale data risk
- Monitor cache eviction; if high, increase cache size or change TTL
- Load test should include realistic data distribution (not uniform)
- Be cautious with aggressive optimization; sometimes simpler is better
- Plan for scaling early (think 10x growth)
