## ✅ ACCEPTANCE CRITERIA

### Given-When-Then Format

**Given** the database is configured
**When** I implement RBAC and encryption
**Then** access control should be:
- Read-only role for reporting (SELECT only)
- Limited-write role for application (SELECT, INSERT, UPDATE on specific tables)
- Admin role for migrations (Full access, requires MFA)
- No superuser access for application
- Passwords stored in AWS Secrets Manager
- Rotated every 90 days automatically

**Given** audit logging is configured
**When** database operations occur
**Then** all operations should be logged:
- User/role performing operation
- Operation type (SELECT, INSERT, UPDATE, DELETE)
- Timestamp and duration
- Rows affected
- Connection IP address
- Stored in `audit_logs` table for 1 year retention

**Given** encryption is enabled
**When** data is stored and transmitted
**Then** encryption should cover:
- At-rest: All data encrypted with KMS key (AES-256)
- In-transit: TLS 1.2+ for all connections
- Secrets: Passwords and API keys in AWS Secrets Manager
- Application logs: No sensitive data (PII, passwords, tokens)

**Given** the application is running
**When** a security event occurs
**Then** it should:
- Log security events to CloudWatch
- Alert on failed authentication attempts (5+ in 5 min)
- Alert on unauthorized access attempts
- Alert on privilege escalation attempts
- Generate security audit report daily

## 📋 TASKS

### Task 3.5.1: Database Role-Based Access Control (RBAC)
- [ ] Create PostgreSQL roles:
  - [ ] `reset_primal_app` - Application user (SELECT, INSERT, UPDATE on specific tables)
  - [ ] `reset_primal_reporting` - Read-only role for analytics
  - [ ] `reset_primal_admin` - Admin role (requires MFA override)
- [ ] Grant minimum required permissions:
  - [ ] `app_user`: All on users, purchases, products; None on audit_logs
  - [ ] `reporting_user`: SELECT only on users, purchases, products, analytics
  - [ ] Deny all direct table access by default
- [ ] Create connection limit per role: Max 20 concurrent per user role
- [ ] Test role permissions: Verify app user cannot modify audit_logs
- [ ] Document role permissions matrix in SECURITY.md

### Task 3.5.2: Audit Logging Implementation
- [ ] Create `audit_logs` table in database:
  ```sql
  CREATE TABLE audit_logs (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID,
    operation VARCHAR(10),
    table_name VARCHAR(255),
    record_id UUID,
    old_values JSONB,
    new_values JSONB,
    ip_address INET,
    user_agent VARCHAR(500),
    created_at TIMESTAMP DEFAULT NOW(),
    INDEX idx_created_at (created_at),
    INDEX idx_user_id (user_id)
  );
  ```
- [ ] Implement database trigger for audit logging on all tables
- [ ] Configure log retention: Keep 1 year, auto-archive to S3 cold storage
- [ ] Create Prisma model for audit_logs (read-only, for inspection)
- [ ] Implement audit log query API endpoint (admin only):
  - [ ] Filter by user_id, date range, operation type
  - [ ] Return paginated results
- [ ] Test audit logging: Verify operations are logged correctly
- [ ] Performance: Audit logging should add < 10ms latency

### Task 3.5.3: Encryption Setup (At-Rest & In-Transit)
- [ ] Configure TLS 1.2+ for PostgreSQL:
  - [ ] Generate or import SSL certificate
  - [ ] Set `ssl = on` in PostgreSQL config
  - [ ] Require SSL: `ssl_prefer_server_ciphers = on`
  - [ ] Test: Verify connection fails without SSL
- [ ] Enable at-rest encryption:
  - [ ] RDS: Enable AWS-managed encryption (default)
  - [ ] Or: Use pgcrypto extension for column-level encryption
- [ ] Set up AWS KMS key for backups encryption
- [ ] Implement application-level encryption for sensitive fields:
  - [ ] Passwords: Already hashed with bcrypt
  - [ ] Email addresses: Encrypt in database column
  - [ ] Consider: Tokenization for PII (customer names)
- [ ] Test: Verify encrypted fields cannot be read without key

### Task 3.5.4: Secrets Management
- [ ] Store secrets in AWS Secrets Manager:
  - [ ] Database password for `app_user`
  - [ ] Database password for `admin_user`
  - [ ] Hotmart webhook secret
  - [ ] SendGrid API key
  - [ ] GA4 API secret
  - [ ] SSL certificate (optional, can be in ECS task definition)
- [ ] Create IAM role for application to read secrets
- [ ] Configure secret rotation:
  - [ ] Database password: Auto-rotate every 90 days
  - [ ] API keys: Manual rotation every 180 days
- [ ] Retrieve secrets in application at startup (not from .env in production)
- [ ] Never log secret values (mask in logs)
- [ ] Test: Application starts and connects using rotated secret

### Task 3.5.5: Application-Level Security Hardening
- [ ] Update application configuration:
  - [ ] Helmet.js headers (already enabled, verify all security headers)
  - [ ] CORS: Restrict to frontend domain only
  - [ ] CSRF protection: Enable if using sessions
  - [ ] Rate limiting: 100 req/minute per IP (already implemented)
- [ ] Input validation:
  - [ ] Validate all user input
  - [ ] Sanitize before database operations
  - [ ] Reject invalid data types (SQL injection prevention)
- [ ] Error handling security:
  - [ ] Don't expose database errors to users
  - [ ] Log full errors internally
  - [ ] Return generic "Invalid request" to client
- [ ] Authentication hardening:
  - [ ] Implement MFA for admin/sensitive operations
  - [ ] Session timeout: 30 minutes
  - [ ] Logout: Invalidate JWT tokens
- [ ] Dependency security:
  - [ ] Run `npm audit` and fix vulnerabilities
  - [ ] Keep dependencies up to date
  - [ ] Monitor security advisories

### Task 3.5.6: Security Monitoring & Alerting
- [ ] Set up CloudWatch alarms for security events:
  - [ ] Failed authentication: 5+ attempts in 5 minutes → Alert
  - [ ] Privilege escalation: Admin role used from unexpected IP → Alert
  - [ ] Bulk delete/update: > 1000 rows in single operation → Alert
  - [ ] Backup failure: Backup did not complete → Critical Alert
- [ ] Create application security log group in CloudWatch
- [ ] Implement security event logging in application:
  - [ ] Failed login attempts (email + timestamp)
  - [ ] Admin actions (user ID, action, timestamp)
  - [ ] API key usage (which key, when, for what)
- [ ] Create daily security audit report:
  - [ ] Summary of authentication attempts (success/failure)
  - [ ] Admin actions performed
  - [ ] Any security alerts triggered
  - [ ] Email to security team
- [ ] Document security incident response procedure
